Demonstration controls

Presentation scaffolding, not product functionality. These controls exist so the novelty features can be triggered on stage without waiting for real weather or real payment settlement.

This screen would not exist in a deployed system. It is here because a live demo needs every condition to be reproducible on demand.

Re-run data validation

Runs the Aadhaar checksum, bank format, IFSC format, name-match and land-record checks across every registered farmer and rebuilds the mismatch queue.

Settle in-flight payments

Moves every transaction sitting in processing to completed, as the DBT gateway would after a couple of days. Useful for showing the farmer-side payment view updating during a demo.

Queued voice calls

Every alert the portal raises for the phone channel is queued here. Calls go straight from this machine to Vonage, so there is no second server to start and nothing to keep awake.

Phone channel

Outbound calls (we ring the farmer) are handled here in the portal, and need no public URL because the spoken message is sent inline with the request.

Inbound (the farmer rings us) is parked until we have a number to publish. The half-built menu lives in farmer-ivr/, and this feed is what it reads:
